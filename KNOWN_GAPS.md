# Known gaps

Things that are missing or incomplete right now, tracked here instead of in [CHANGELOG.md](CHANGELOG.md) since they're about the current state of the project rather than what changed in a given release.
Not blocking — just not built yet.

- Notes UI (creating/editing note-only entries) is built at the data layer but currently disabled in the UI pending a better interaction design.
- No tags or screenshots-per-entry.
- No Chrome Web Store listing — load-unpacked only.
- No automatic trash expiry (e.g. "permanently delete after 30 days"). There's currently no server-side scheduling mechanism at all — the Worker only has an HTTP `fetch` handler, no `scheduled()` handler / Cron Trigger — and a retention policy is inherently a server-side, device-independent setting (a per-device toggle wouldn't make sense for something that should run whether or not any client is even open). Feasible via Cloudflare's Cron Triggers, but real new infrastructure, not a small addition; permanent delete itself (manual, per-item/bulk/empty-trash) is built — see `worker/src/index.ts`'s `?permanent=true` and `worker/migrations/0003_cascade_delete.sql`.
- Switching a device's Worker URL/token doesn't clean-swap the local experience: the `Store`'s cached state (`chrome.storage.local` on the extension) isn't cleared on change, so the next sync merges (unions) local data into the new Worker rather than starting fresh against it — see `mergeState()` in `core/lib/sync.ts`.
- Still-thin automated coverage for the DOM-orchestration layer: `core/ui/*.ts` (`folders.ts`, `trash.ts`, `rail.ts`, `folderPicker.ts`, `toolbar.ts`), `extension/src/options/main.ts`, `popup/main.ts`, `background/background.ts` have no `*.test.ts` and aren't touched by the e2e suite either — none of it has regression protection for drag-and-drop reordering, multi-select, or the trash restore flow. `core/lib/*` (storage, sync, modal, tobyImport, linkMetadata, plus small extracted helpers like url/time/theme/backupFile/actions/favicon/uiState/config/store) is well covered by unit tests; `extension/src/newtab/tabsPanel.ts` now has a narrow regression test too (`tabsPanel.test.ts`, covering the tab-closing-via-`ctx.tabActions.close` seam specifically), but that's one targeted case, not general coverage of the live `chrome.tabs` sync panel.
  Plain jsdom/happy-dom unit tests wouldn't actually catch what's broken most often here: every real bug found in this code during development (Playwright's simulated drag not firing real HTML5 DnD events, position-collision on restore, a timestamp-equality assumption that broke under `Date.now()`'s 1ms resolution) was a genuine browser/event-timing issue, not a logic bug behind a clean interface — this code is fundamentally about DOM/browser orchestration, not algorithms.
  A small Playwright e2e suite now exists and is CI-wired (`extension/e2e/`, run via `npm run test:e2e --workspace=extension`, its own `e2e` job in `.github/workflows/ci.yml` under `xvfb`) — but it only covers two smoke flows (folder/link creation + reload-persistence, entry multi-select's action bar + delete). The higher-risk flows still without any coverage: folder/entry drag-reorder, tabs-panel multi-select + save, live `chrome.tabs` sync, trash restore. Extending `extension/e2e/` with specs for those is the natural next step, reusing the same `fixtures.ts` (real built extension, real headed Chromium).
- No keyboard shortcuts help modal (e.g. pressing `?` to see a cheat sheet). Not worth building yet — there's currently only one real shortcut (`/` to focus search, Escape to clear it) — but revisit once there are enough shortcuts that they're not all self-evident from the UI.
- The web app's drag-and-drop reordering (folders and entries) works on desktop — it's the same shared `core/ui/folders.ts` code and native HTML5 drag events as the extension, with no platform-specific gating. It doesn't work via touch, though: there's no `touchstart`/`touchmove` handling anywhere in `core/` or `web/`, and mobile browsers don't fire HTML5 drag events from touch gestures without one. A real touch-friendly interaction (long-press-to-drag, or a reorder-mode toggle) is still a deliberately deferred task — folders/entries can still be created, renamed, deleted, and moved between folders via buttons/modals on a touchscreen, just not reordered by dragging.
- The web app has no PWA installability — no install manifest, no service worker, no offline-after-first-load beyond whatever the browser's own HTTP cache provides.
- Multi-tab write races in the web app, partially mitigated: `core/lib/storage.ts` reads/writes the entire `State` blob under one key with no per-record granularity, so two browser tabs saving within the same instant still last-write-wins with no true conflict merging. A `BroadcastChannel`-based reconciliation (`web/src/webStore.ts`) closes the _silent, indefinite_ divergence case — a tab left open picks up another tab's change almost immediately — but doesn't add real conflict resolution. Same residual risk class as the extension's analogous two-newtab-windows scenario.
- No user-visible error handling for storage-write failures throughout `core/ui/*.ts` (folders, toolbar, rail, trash, folderPicker) — every `ctx.rerender()`/`pushResource` call after a create/rename/delete/move assumes the underlying `Store.set()` succeeds. It usually does, but both backends have a real quota: `chrome.storage.local` defaults to ~10MB (no `unlimitedStorage` permission is requested), and IndexedDB's much larger best-effort browser quota can still be hit or blocked. If a write fails (quota exceeded, blocked transaction), the in-memory UI has already applied the change but it's silently never persisted — the edit appears to work and then reverts on the next reload with no error shown. The options page's and web app's own Save/Disconnect buttons got targeted fixes for this exact failure mode, but the general case (any edit inside the shared folder-browser UI) doesn't have a surfacing mechanism yet — would need a toast/banner system in `core/ui/` shared by both platforms, not a one-off fix.
- `npm run setup`/`npm run upgrade` (`scripts/wizard/`) assume an interactive TTY — no non-interactive/CI mode (e.g. answering prompts from environment variables or a config file for scripted deployments).
- The wizard scripts shell out to the `wrangler` CLI and parse its stdout (login status from `whoami`, JSON from `d1 list`/`d1 create`, a printed URL from `deploy`/`pages deploy`) rather than a stable programmatic API — a future Wrangler CLI output-format change could silently break this parsing. Failures here degrade to a warning and the raw output rather than a crash, but the extracted value (URL, database_id) would be missing.
- A fresh device (or one that's wiped local storage) can resurrect an intentionally-deleted default workspace: `core/lib/storage.ts`'s `initState()` always auto-creates a "Home" workspace under the same fixed id (`DEFAULT_WORKSPACE_ID = "default"`, so independently-first-run devices converge on sync), timestamped `Date.now()`. If that id was later soft-deleted on the Worker (e.g. a duplicate cleaned up by hand), `mergeArray`'s plain "newer `updated_at` wins" rule means the freshly-created local copy — always newer than an already-past deletion — wins the merge and comes back non-deleted. There's no tombstone precedence in the sync design (see `core/lib/sync.ts`'s `mergeArray` doc comment) to prevent this. Not fixed at the code level yet — the real fix would mean deferring the local auto-create until after an initial pull confirms there's nothing usable remotely, which touches every `loadState()` call site's assumptions about a workspace always existing. Worked around for now by making sure any account's real default workspace's id is genuinely `"default"` in the Worker, so there's nothing left to collide with.
